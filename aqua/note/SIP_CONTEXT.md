# Sip App Context

## Overview
Sip is a minimal water-tracking iOS app. Tap a button, log a sip, watch the screen fill with water that drains over 2 hours. A Home/Lock Screen widget mirrors hydration and lets you log directly. App name toggles: **"Aqua"** (水) when hydrated, **"Sip"** (飲) when dehydrated. Bilingual EN + 中文 throughout.

## Tech
- **Platform:** iOS 26.2, iPhone & iPad
- **Language:** Swift 5, `@Observable`, async/await, App Intents
- **UI:** SwiftUI only, fixed light color scheme (theme-driven)
- **Architecture:** MVVM — `WaterStateViewModel` (`@Observable`) drives `ContentView`
- **Persistence:** `UserDefaults` via App Group (`group.andychudesign.Aqua`), shared between app and widget
- **Widget:** `AquaWidgetExtension` — `SipHomeWidget` (small/medium) + `SipStatusWidget` (circular/rectangular accessory)
- **Fonts:** Inter-Medium app-wide (referenced via `Font.custom("Inter-Medium", ...)` — **not yet bundled**, silently falls back to system). Crimson Text Regular + SemiBold bundled in `aqua/Resources/Fonts/` and registered at launch via `CTFontManagerRegisterFontsForURL` (see `BundledFonts.registerAll()` in `aquaApp.swift`, called from `aquaApp.init()`), used for the Kurosawa theme name in the gallery preview.
- **Frameworks:** SwiftUI, Foundation, WidgetKit, AppIntents, HealthKit, AVFoundation, CoreText

## Core Logic
- **Single data point:** `lastWaterLogTime` (Date in shared App Group `UserDefaults`)
- **Hydration formula:** `hydrationLevel = max(0, 1 - elapsed / 7200)` — linear decay 1.0 → 0.0 over 2 hours
- **Log sip:** Sets `lastWaterLogTime` to now → hydration jumps to 1.0 → begins draining
- **Refresh:** 1s timer in VM recalculates `hydrationLevel`; refreshes on `scenePhase == .active`
- **Widget sync:** `WidgetCenter.shared.reloadAllTimelines()` after each log; provider pre-computes 5-minute drain entries

- **Bug 7 fix part 2 (v1.4 follow-up):** the home widget would update to 100% after a widget-tap sip but the lock-screen widget could remain stuck at 0% even after Bug 7's timeline rework. Two changes:
  1. **Explicit per-kind reloads.** `WidgetCenter.shared.reloadAllTimelines()` is silently coalesced/deferred for the accessory family on iOS 26 when issued from inside an `AppIntent.perform()` that still has an `await` ahead of it. Every sip-logging site (`LogWaterIntent.perform()`, `LogWaterAuthIntent.perform()`, `SharedStorage.logWater()`) now follows `reloadAllTimelines()` with explicit `reloadTimelines(ofKind: "AquaWidget")` + `reloadTimelines(ofKind: "SipStatusWidget")` calls. `LogWaterIntent` also re-issues the `SipStatusWidget` reload *after* the HealthKit `await` resumes, since the pre-await reload can land while the intent is suspended and get dropped for accessory widgets.
  2. **Accessory entry uses `logTime` as its date.** In `AquaTimelineProvider.getTimeline`, the single accessory-widget entry was previously `date: now, hydrationLevel: Self.hydrationLevel(at: now)`. Two issues with that: (a) `now` is captured at function-entry but the entry isn't visible to WidgetKit until the completion handler is invoked, so on iOS 26 the entry occasionally appears as "current = future" and WidgetKit falls back to the pre-sip cached timeline; (b) `Self.hydrationLevel(at: now)` re-reads `UserDefaults` on a fresh `Date()` instead of reusing the locally-computed `elapsed`, opening a tiny race window. New shape: `date: logTime, hydrationLevel: max(0, 1 - elapsed / hydrationDuration)` — `logTime` is unambiguously in the past (it's the timestamp the sip was recorded at) and the level is computed from the already-validated `elapsed`. Home widget ramp behavior is unchanged.

- **Adaptive status bar glyphs (UIKit window trait, NOT SwiftUI's `.preferredColorScheme`)** — the time, signal, wifi, and battery icons flip between dark and light content the moment the water surface rises into the status bar's safe-area inset, restoring legibility against both themes' dark `waterColor` (Default's deep blue and Kurosawa's near-black). This took **three attempts** because SwiftUI's `.preferredColorScheme` bridge to UIKit's status bar is fundamentally broken for dynamic updates in our setup — the saga is worth recording in detail because every "obvious" fix runs into the same wall.

  - **Geometry check (unchanged across all three attempts):** `ContentView`'s outer `GeometryReader` computes `waterCoversStatusBar = waterSurfaceY <= max(0, statusBarBottom - 6)`. The 6pt padding completes the swap a beat before the wave's trough would otherwise expose the light `dehydratedBackground` under the glyphs.

  - **Attempt 1 — conditional `.preferredColorScheme` (FAILED, partial).** The first attempt was `.preferredColorScheme(waterCoversStatusBar ? .dark : theme.preferredColorScheme)` on the root view, with a `.animation(.easeInOut(duration: 0.25), value: waterCoversStatusBar)` modifier. This **worked for ~1 second after a sip and then snapped back to dark glyphs**. SwiftUI's bridge from `.preferredColorScheme` to `UIHostingController.preferredStatusBarStyle` fires at initial render but doesn't reliably re-propagate when the bound value changes mid-session — when the VM's 1s refresh timer ticked and rebuilt the body, the bridge didn't re-push and UIKit reverted.

  - **Attempt 2 — custom `UIHostingController` subclass (FAILED, no effect).** Switched `aquaApp.swift` from SwiftUI `App`/`WindowGroup` to a UIKit `@main AppDelegate` + `SceneDelegate` that installed a `SipHostingController<ContentView>` as the root view controller, with `preferredStatusBarStyle` reading from a `@MainActor StatusBarStyleController` singleton. `ContentView` pushed `.lightContent`/`.darkContent` via `.onChange` + `.onAppear`; the singleton's `didSet` walked every `UIWindowScene` and called `setNeedsStatusBarAppearanceUpdate()` inside a `UIView.animate(withDuration: 0.25)`. Even after also overriding `childForStatusBarStyle` to return `nil` (so the hidden SwiftUI child controller couldn't intercept), **glyphs stayed dark**. Most likely cause: the surviving `.preferredColorScheme(theme.preferredColorScheme)` on the root view was *still* bridging an explicit `preferredStatusBarStyle = .darkContent` into our subclass — and an explicit return value beats trait-based fallback every time. (Independently, `INFOPLIST_KEY_UIApplicationSceneManifest_Generation = YES` may have generated a scene manifest that bypassed our `application(_:configurationForConnecting:)` and re-installed a default SwiftUI hosting controller; never definitively confirmed because attempt 3 sidestepped the question.)

  - **Attempt 3 — `UIWindow.overrideUserInterfaceStyle`, no SwiftUI bridge (SHIPPED).** Reverted `aquaApp.swift` back to the simple SwiftUI `App` / `WindowGroup` lifecycle — `BundledFonts.registerAll()` is back in `aquaApp.init()`, and the entire `AppDelegate`/`SceneDelegate`/`SipHostingController`/`StatusBarStyleController` stack is gone. **Dropped `.preferredColorScheme(theme.preferredColorScheme)` from `ContentView` entirely.** With no explicit style coming from SwiftUI, `preferredStatusBarStyle` falls back to `.default`, which UIKit resolves against the trait collection — and the trait collection is exactly what `UIWindow.overrideUserInterfaceStyle` controls (the same hook the home indicator's automatic contrast adapt hangs off of). New `ContentView.setStatusBarLightContent(_:)` helper finds the key window via `UIApplication.shared.connectedScenes` and swaps its `overrideUserInterfaceStyle` between `.light` (default — also pins the app to its intended light identity for users on system-wide Dark Mode) and `.dark` (water covers status bar → trait collection becomes dark → glyphs render light). Wrapped in `UIView.animate(withDuration: 0.3)` so the fade is in lockstep with the rising water. Driven by `.onChange(of: waterCoversStatusBar)` + `.onAppear` on the root view.

  - **Side effect of dropping `.preferredColorScheme(.light)`: `SipVolumeSheet` would inherit the dark trait** while presented during the brief high-water window, dragging its `.secondary` / `.tertiary` text and system-coloured `NavigationStack` chrome into dark mode. **Fix:** pinned `SipVolumeSheet` itself to `.preferredColorScheme(.light)`. `ThemeGalleryView` was already `.preferredColorScheme(.dark)` so it's unaffected. `ContentView` only uses explicit theme colours so it doesn't care which way the trait goes.

  - **Key takeaway for future status-bar work in this codebase:** if you find yourself reaching for `.preferredColorScheme(...)` to control the iOS status bar, **don't** — it's the trap that ate two attempts here. Use `UIWindow.overrideUserInterfaceStyle` with `preferredStatusBarStyle` falling back to `.default`, and pin individual surfaces with their own `.preferredColorScheme` modifier when they need to opt out of the window-wide trait.

- **Stats overlay hides side buttons** — `sipVolumeButton` and `themeSwitchButton` in `controlRow` now fade out via `.opacity(showStats ? 0 : 1)` + `.allowsHitTesting(!showStats)` while the stats overlay is open.     1. **`Task { @MainActor in setAlternateIconName(...) }`** — broke icon swapping because the async hop landed mid-dismiss of the gallery's `fullScreenCover`; iOS 26 silently no-ops `setAlternateIconName` during view-controller transitions, dropping both the swap and the alert.
    2. **Deferring to `.fullScreenCover.onDismiss` + `DispatchQueue.main.asyncAfter(0.45s)`** — superficially "cleaner" because it waits past the cover's exit animation, and it *did* unblock the `.default → .kurosawa` direction. But **iOS 26.1+ shows the "App Icon Changed" alert via SpringBoard's out-of-process overlay, and SpringBoard only posts it when the underlying `setAlternateIconName(_:)` call originates from a user-interaction context** (see [Apple Developer Forums thread 822359](https://developer.apple.com/forums/thread/822359), where the call now triggers `sceneWillResignActive`).     3. **Synchronous-inline with `.default → nil`** (= `setAlternateIconName(nil)` to revert to primary) — kurosawa direction worked, but the **revert-to-primary path is broken on `.icon`-bundle alternates in iOS 26**. Symptom: the call returns with no error, `alternateIconName` reports nil afterward, but the home-screen icon doesn't update; SpringBoard's alert is also suppressed for this path. Restart sometimes helps for a session but doesn't survive a state change. **The fix is to never call `setAlternateIconName(nil)` at all** — ship `Sip-Aqua.icon` as a duplicate of the primary `Sip.icon` and route the `.default` theme through `setAlternateIconName("Sip-Aqua")` so every swap is a regular alternate-to-alternate transition. iOS 26 handles those reliably, and SpringBoard posts the alert in both directions.

    Current shape:
    - `WaterStateViewModel.applyTheme(_:)` persists `SharedStorage.selectedThemeID`, updates the in-memory `theme`, *and* — when the id actually changes (`previousID != id` guard) — synchronously calls `UIApplication.shared.setAlternateIconName(_:)` with a completion-handler that prints any error to the console.
    - `ThemeID.alternateIconName` is `String` (non-optional). Adding a theme = add a `case` returning a new alternate name + ship the corresponding `.icon` bundle + add the name to `ASSETCATALOG_COMPILER_ALTERNATE_APPICON_NAMES`. The non-optional type makes the "never `nil`" rule a compile-time invariant.
    - The gallery's action pill keeps the order `onApply(selectedID)` *then* `dismiss()` so the UIKit call lands while we're still inside the SwiftUI button action (user-interaction context, required for SpringBoard's alert).
    - The `fullScreenCover` has **no** `onDismiss:` callback for icon work.
    - **Do not** guard on `UIApplication.shared.alternateIconName == desired` — that property can disagree with the real home-screen icon (stale `nil`, delayed updates, iOS quirks) and previously caused `setAlternateIconName` to be skipped forever even after a theme change. The `previousID != id` guard on the *persisted* id is the right shape.
    - **If a swap is still failing**, watch the Xcode console for `[Aqua] setAlternateIconName(...) failed: ...`. Persistent failures (NSPOSIXError 35) after a theme change usually mean the simulator's icon-cache is in a bad state — restart the simulator or test on a real device. `UIKit` import remains for `UIApplication`.
  - **Widget icons are unaffected** — alternate icons only swap the home-screen launcher icon. The widget's own theming continues to flow through `AquaWidgetEntry.themeID` exactly as before.

Replaced with `.preferredColorScheme(systemScheme)` where `systemScheme` is captured via `SipVolumeSheet.detectSystemScheme()` — reads `UIWindowScene.screen.traitCollection.userInterfaceStyle`, which is **unaffected by window-level overrides** (the override only mutates the *window's* trait, not the screen's). Captured on init, refreshed on `.onAppear` and on `scenePhase == .active` (so swiping down to Control Center → toggling Dark Mode → coming back updates the sheet). `ThemeGalleryView` continues to pin itself to `.dark` (its own customisation surface) and was never affected.
- **Realistic water rendering in the main app (v1.4)** — `waterFillView` evolved from a single `WaveShape.fill(theme.waterColor)` into a 4-layer ZStack for a more "liquid" look while keeping the architecture pure-SwiftUI (no Metal, no SpriteKit, no third-party deps — open-source SwiftUI "water" libs all turned out to be the same sine-wave shape we already had). Layers, from back to front:
  1. **Solid body** — `WaveShape(...).fill(theme.waterColor)`. Parameters (phase / amplitude / frequency=1.5 / bumpHeight / bumpWidth=0.18) are kept *exactly identical* to the ones `waterShapeMask(screenHeight:bumpHeight:)` uses, so the dual-layer text color split (`headerPrimary` vs `headerPrimaryOnWater`, stats text, close button) stays pixel-perfect on the visible waterline. Touching those numbers will silently desync the mask — don't.
  2. **Vertical depth gradient** — `LinearGradient` (white 0.06 at top → clear at 25% → black 0.14 at bottom), clipped to `bodyShape` via `.clipShape`. Adds volumetric depth so the water reads as a slab, not a flat color. White/black tints work for both Default (blue) and Kurosawa (charcoal) palettes without theme tokens.
  3. **Subsurface glow band** — `WaveCrestShape` (new) stroked with `white.opacity(0.10)`, lineWidth 10, blur 6, offset down 6pt, clipped to `bodyShape`. Fakes light penetrating just below the surface, like the bright band you see under a real water meniscus.
  4. **Specular sheen** — same `WaveCrestShape` stroked with `white.opacity(0.32)`, 1pt, blur 0.4. Crisp highlight riding the crest. Not clipped — it sits right on the waterline.
- **`WaveCrestShape: Shape` (new)** — open path that traces only the top surface curve, no closure, no sides. Used by layers 3 + 4 above so a `.stroke(...)` only draws the crest, not the entire wave outline. Same `animatableData` shape as `WaveShape` (amplitude + bumpHeight) so it animates in lockstep when `sloshAmplitude` springs after a sip.
- **`waveSurfaceY(...)` free helper** — shared inlined surface formula extracted out of `WaveShape.path` and now also called by `WaveCrestShape.path`. Single source of truth for the dual-sine + Gaussian-bump curve.
- **Widget unchanged** — the realism upgrade is main-app only. Widget rendering glyphs are too small for the gradient + sheen layers to read, and WidgetKit has stricter perf budgets for timeline reloads. `AquaWidgetExtension/AquaWidget.swift` still uses the single-layer `WaveShape.fill(theme.waterColor)`.
- **Gallery preview cards unchanged** — `ThemePreviewCard` (in `ContentView.swift`, used inside `ThemeGalleryView`) still uses a single `WaveShape.fill(theme.waterColor)`. Cards are small + many on-screen during scrolling; the extra layers would cost noticeably more without adding much at that size.

The right model is the opposite: swap text to the on-water color a bit **before** the water reaches it, so the title/sip-count stay legible across the entire approach window. At 0.75 the wave crest sits well below the title (`y ≈ widgetHeight * 0.25`, comfortably under the ~y=16–31 text band on any common widget size), giving a generous safety margin against tall medium widgets and wave amplitude.

The "Free" string + onUnlock callback are the two seams the v2.0 StoreKit work will replace with a real `Product.displayPrice` and `purchase()` flow; the perks + disclaimer layout can stay as-is.

- **Why `UnlockThemeSheet` is NOT a native `.sheet`** — first pass used SwiftUI's `.sheet(isPresented:)` with `.presentationDetents([.fraction(0.62)])` + `.presentationBackground(.ultraThinMaterial)` + `.presentationCornerRadius(36)` + `.presentationBackgroundInteraction(.enabled)`. Two problems killed that approach on iOS 26.2 and pushed us to a custom bottom-anchored overlay:
  1. **iOS 26's "floating" sheet style reserves horizontal margins on larger devices** (iPhone 16 Pro included), making the sheet visibly inset from the gallery edges. There's no public API to force edge-to-edge — neither `presentationCornerRadius` nor `presentationCompactAdaptation` overrides the margin. This broke the design's full-width feel.
  2. **`.ultraThinMaterial` rendered as flat dark gray** with no visible blur of the gallery underneath. Root cause: iOS applies a non-removable system dim layer behind every sheet, sitting between the sheet's background and the presenter. The material samples that dim-on-black instead of the actual gallery cards. `.presentationBackgroundInteraction(.enabled)` removes the *interaction* block but keeps a visual dim that the material still picks up.

  Replacement: `ThemeGalleryView`'s outer `ZStack` includes a full-screen `GeometryReader` (`unlockOverlay`) that **stays mounted** even when the sheet is hidden. Inside, a `ZStack(alignment: .bottom)` layers (a) a `Color.black` whose `opacity` animates between `0` and `0.55` with `.ignoresSafeArea()` + tap-to-dismiss (darkens the gallery when active), and (b) `UnlockThemeSheet` with `.offset(y: showUnlockSheet ? 0 : max(geo.size.height, 1))` so the card slides up from / down off the bottom — the same mechanical motion as the system `.sheet` stack used by `SipVolumeSheet`. A single `.animation(Self.sheetSpring, value: showUnlockSheet)` on that inner `ZStack` drives both the opacity and the offset; every mutation site (`actionPill`, backdrop tap, `Unlock now`) just assigns `showUnlockSheet` — no `withAnimation` at each call site. The overlay root applies `.allowsHitTesting(showUnlockSheet)` so when dismissed, touches pass through to the carousel. **Why not `if showUnlockSheet { … }` + `.transition(.move(edge: .bottom))`:** SwiftUI often fails to run removal transitions for multi-view conditional branches inside a `ZStack`, so dismiss looked instant; `offset` animation is reliable.

  `UnlockThemeSheet` carries its own surface treatment: content has `.padding(.bottom, 28)` for home-indicator clearance, then `.frame(maxWidth: .infinity) + .frame(height: 520)` to match the previous `.fraction(0.62)` detent on iPhone 16-class devices. The rounded glass background is built in a `.background { … }` closure: a top-only `UnevenRoundedRectangle` (36pt top corners, 0pt bottom corners) `.fill(.ultraThinMaterial).ignoresSafeArea(edges: .bottom)`. **Why the shape lives in `.background { }` instead of `.background(.ultraThinMaterial) + .clipShape(...) + .ignoresSafeArea(...)` on the outer view:** that earlier form clipped the material at the 520pt frame *first*, then the outer `.ignoresSafeArea(edges: .bottom)` tried to extend the view into the home-indicator safe area — but the content was already clipped, leaving an empty band at the bottom that read as a black gap with the backdrop dim showing through. Moving the shape into the background slot and letting *the background* (not the outer view) ignore the safe area keeps the content frame at 520pt while the material genuinely extends to the screen edge.

  With no system dim layer in the way, the material now genuinely blurs the carousel cards visible beside the centered card. Trade-off: we lose the system swipe-down-to-dismiss gesture; exits are tapping the backdrop or tapping "Unlock now". Acceptable for a single-action offer card — if we ever want swipe-to-dismiss back, layer a `DragGesture` on the sheet content.

### Bug fix — lock-screen widget not updating immediately after a sip
- **Symptom:** after logging via the home-screen widget, the lock-screen (accessory) widget's water level + status lagged. Worst when both accessory sizes (circular + rectangular) were installed and when several sips were logged in quick succession.
- **Root cause:** the home widget that owns the tapped button is auto-reloaded by WidgetKit on intent return; accessory widgets don't contain the button so they rely entirely on explicit `reloadTimelines`, which is metered by WidgetKit's per-widget reload budget. Every sip site charged the `SipStatusWidget` budget **3×** (`reloadAllTimelines()` + a per-kind call + a second per-kind call after the `await`). Two accessory widgets × multiple rapid sips exhausted the budget, so later accessory reloads were dropped → frozen lock-screen.
- **Fix:** issue **one** reload per kind, after all shared state is committed (incl. the HealthKit auth flag). Removed the redundant `reloadAllTimelines()` double-charge and the duplicate post-`await` call. Applied to all four sip paths: `LogWaterIntent.perform()` (`AquaWidget.swift`), `LogWaterAuthIntent.perform()` (`SipIntents.swift`), `SharedStorage.logWater()`, and the post-HealthKit re-reload in `WaterStateViewModel.logWater()`. The theme `selectedThemeID` setter keeps `reloadAllTimelines()` (rare, one-off). Net: 3× more accessory budget headroom while preserving the reliable per-kind delivery.

### Widget glass background + Dark Mode (home widget)
- **Goal:** the home widget background (off-white `dehydratedBackground`) didn't support Dark Mode and wasn't the translucent Liquid Glass the user wanted (battery-widget look — wallpaper showing through, light/dark glass per the user's Home Screen appearance setting).
- **The key realisation (after two wrong attempts):** the transparent glass is **system-driven**, not something we paint. Per iOS 26 WidgetKit (WWDC "WidgetKit foundations"), when the Home Screen uses a **tinted or clear (Liquid Glass) appearance**, WidgetKit **removes the view declared in `containerBackground(for:.widget)` and substitutes its own adaptive glass material** (light glass in Light Mode, dark glass in Dark Mode, wallpaper showing through) while tinting widget *content*. Third-party widgets **cannot** render the wallpaper themselves, and in the **default full-color** appearance the system does **not** make them transparent. So `.regularMaterial` / `Color(uiColor:.secondarySystemBackground)` both render as a flat opaque panel — the "same off-white as before" the user kept seeing. Those two earlier attempts were abandoned.
- **Why it wasn't already glassy:** (1) `SipHomeWidget` called `.containerBackgroundRemovable(false)`, explicitly **opting out** of the glass replacement; (2) the **water was drawn inside `containerBackground`**, so even if removal were enabled the water would be removed with the backdrop.
- **Fix — architecture (`AquaWidget.swift`):**
  - **Water is now widget *content*, not the background.** `smallView`/`mediumView` collapse into a shared `homeView`: a `ZStack(alignment:.bottom)` with `waterFill` (the `WidgetWaveShape`) at the back and the header/button `VStack` on top. The container background now holds only `widgetBackground` (the backdrop), so WidgetKit can remove/replace just the backdrop while the water survives (and gets system-tinted like any other content in tinted/clear mode — same as the Batteries ring).
  - **Removed `.containerBackgroundRemovable(false)`** so the glass swap is enabled. Also enables StandBy/iPad-lock contexts.
  - **`.contentMarginsDisabled()`** on the config so the water bleeds edge-to-edge; the header/button reapply the system margins via `@Environment(\.widgetContentMargins)` → `.padding(contentMargins)`. `waterFill` is marked `.widgetAccentable()` so it takes the accent strongly in color-tint mode.
  - **`widgetBackground`** is the full-color fallback only (shown when the Home Screen is in default appearance): adaptive `isDark ? Color(white:0.12) : theme.dehydratedBackground` so it still supports Dark Mode there.
- **Legibility in Dark Mode (full-color path):** added `@Environment(\.colorScheme)` → `isDark`. Off-water header/sip-count/drink-button colors switch to their light (on-water) treatment whenever `headerOnWater || isDark` (button: `buttonOnWater || isDark`). Light-Mode thresholds (`headerOnWater >0.75`, `buttonOnWater >0.15`) drive timing exactly as before; the OR only forces light content when the backdrop is dark. Tinted-mode branches unchanged (keyed on `*OnWater` only). Drink-button colors factored into `buttonForegroundColor`/`buttonBackgroundColor`.

### Siri / App Intents voice actions (V2.0)
- **Framework choice:** uses **App Intents + `AppShortcutsProvider`** (the modern Siri surface on iOS 26), *not* legacy SiriKit (`INIntent`/`Intents.framework`). The app already shipped App Intents (`LogWaterAuthIntent`, widget `LogWaterIntent`), so this is the consistent, supported path. No Info.plist work needed — `appintentsmetadataprocessor` auto-extracts the shortcuts at build time (`Metadata.appintents`).
- **New file:** `Core/SiriShortcuts.swift` — **app-target only** (snippet `View`s + `AppShortcutsProvider` must run in the host app process; the synchronized root group adds the file to the `aqua` target automatically and it is *not* in the widget's `membershipExceptions`). Holds two intents (`LogSipIntent`, `WaterIntakeQueryIntent`), the `SipTrend` / `DayQuery` models, two snippet views, and `SipShortcutsProvider`.
- **`LogSipIntent`** (`openAppWhenRun = false`, background) — logs a sip via `SharedStorage.logWater()` (same persistence + per-kind widget reload as every other sip path), then `await HealthKitManager.saveSip(requestAuth: true)` (silent no-op if auth not yet granted from the background Siri context; sip still recorded locally + in widgets; on success sets `healthKitAuthResolved` and re-reloads both widget kinds to rebind the widget button to the background intent). Returns `.result(dialog:view:)` with a spoken confirmation + the `SipLoggedSnippet`.
- **`WaterIntakeQueryIntent`** (`openAppWhenRun = false`) — takes **`@Parameter day: DayQuery`** (default `.today`) for **today / yesterday / any weekday / this week / last week**. Day paths resolve a single date; week paths aggregate calendar-week totals via `SharedStorage.WeekScope`. Returns `.result(dialog:view:)` with spoken summary + `WaterIntakeSnippet`.
- **`DayQuery: AppEnum`** — fixed enum (`today`, `yesterday`, `monday…sunday`) so Siri matches the spoken day from the phrase's `\(\.$day)` token without a disambiguation round-trip. Carries `calendarWeekday` (Sun=1…Sat=7), `dialogSubject` ("Today"/"Yesterday"/"On Monday"), and `snippetSubject` ("Monday").
- **Per-day storage lookups (`SharedStorage`)** — `dateKey(for:)`, `sipCount(on:)` (today → live counter, earlier days → `sipHistory`), `estimatedVolumeML(on:)` (today → actual `todayTotalVolumeML`; earlier days → **estimated** as count × current per-sip volume, since no per-day volume history is persisted — matches the app's existing migration-fallback convention).
- **`SipTrend`** — compares a day's count to the rest-of-week average. `Direction` ∈ `{up, down, flat (within ~8%), noData}` + an absolute `percent`. Drives the spoken clause, the snippet's SF Symbol + label, and tint color. `noData` when there's no comparison history.
- **`SipLoggedSnippet`** — Siri result card that fills with water **0 → 100** on appear (the "lock-screen widget" feedback the user asked for). `@State fill: Double` animates via `withAnimation(.easeOut(1.4))` in `.onAppear` (animates the water `.frame(height:)`); a `TimelineView(.animation)` adds the live wave horizontal motion. The drop icon + two text lines **crossfade** from the dehydrated dark treatment (`theme.headerPrimary` / `theme.waterColor`) to the on-water white treatment via paired `.opacity(1 - fill)` / `.opacity(fill)` layers, so they stay legible across the whole rise (cream→blue). Reuses the app's `WaveShape` (internal, app target). Theme-aware via `SharedStorage.currentTheme`.
- **`WaterIntakeSnippet`** — chosen day's sip count + total mL, a 7-day mini bar chart (the chosen day highlighted in `waterColor`, others `statsSecondary.opacity(0.5)`), and the trend label. `ForEach` keyed on a small `SipDay: Identifiable` (id = `yyyy-MM-dd` date string) rather than index, per the foreach idiom. **English-only** labels.
- **`SipShortcutsProvider.appShortcuts`** — every phrase contains the required `\(.applicationName)` token (a hard Apple requirement for app-provided shortcuts — a phrase with no app name won't build/register). App display name is **"Sip"**, so log phrases are the natural **"Take a Sip"** / "Log a Sip" / "Add a Sip" (the app name *is* the noun, so no redundant "…in Sip"), and query phrases use **"Sip" as the verb**: "How much water did I Sip \(\.$day)" / "How much did I Sip \(\.$day)" / plain "How much water did I Sip" (defaults to today). **Note:** Siri cannot register a fully app-name-free phrase like a bare "how much water did I drink today" — to get that, the user assigns their own phrase to the shortcut in the Shortcuts app.
- **Language:** all Siri-facing text (dialog + snippets) is English-only. (Earlier drafts had bilingual EN+中文 snippet labels; removed at the user's request.)
- **Testing note:** verified on device by the user (screenshots confirmed both snippets render + animate). Automated device verification can't run in this environment (the Xcode `device-interaction` MCP tools aren't enabled, and Siri voice isn't reliably testable in the Simulator). Manual test: build to a device, then say "Hey Siri, take a Sip" / "Sip, how much water did I drink yesterday", or run the two shortcuts from the **Shortcuts app**.
- **Snippet width on the Siri voice surface is system-capped + leading-aligned (V2.0 follow-up).** Investigated why the result snippets render narrow and pinned to the left after labels went English-only. The Siri/Spotlight snippet **host** proposes an unspecified width, measures the returned view, clamps it to its own maximum card width (~85% of the panel on the tested device), then re-lays-it-out leading-aligned (the clamped card keeps a proper rounded right corner, so it's genuinely laid out at the cap — not clipped). Findings:
  - An intermediate `View.snippetFillWidth()` helper (`.frame(idealWidth: 1000, maxWidth: .infinity)`) **did** widen the cards from their English content width up to the host's max, proving the host caps width — but the residual trailing gap + leading alignment are host-owned and **not overridable** from the app side. This matches WWDC "Design interactive snippets" (snippets keep system-controlled margins; the app styles content, the system owns the outer frame) and the open Apple Forums report of inconsistent snippet width rendering on iOS 26.1/26.2 ([thread 807689](https://developer.apple.com/forums/thread/807689)).
  - True edge-to-edge / re-centering within the full panel is therefore not reliably achievable on the Siri voice surface.
  - **Shipped:** removed the `idealWidth` workaround and adopted Apple's canonical snippet layout instead — `.frame(maxWidth: .infinity)` + `.clipShape(ContainerRelativeShape())` on both `SipLoggedSnippet` and `WaterIntakeSnippet` (replacing the fixed `RoundedRectangle(cornerRadius: 22)`), so the system hands the snippet its container width and concentric corner radius. `ContainerRelativeShape` is the API Apple's design session prescribes for adaptive snippet margins/corners. Inner content + animations unchanged. Note: this can still leave the host left-aligning on builds exhibiting the 26.1/26.2 inconsistency; if so it's a system bug to file feedback on, not an app-side fix.

### Water caustics shader (V2.0)
- **Goal:** bring the *refracted-light look* of Evan Wallace's [WebGL Water demo](https://madebyevan.com/webgl-water/) to Sip's water — animated caustic shimmer over the body. The user explicitly chose the **"caustics / refraction look only"** option (keep the existing wave shape + motion, add a shader for the light look) over a full interactive ripple sim or a 3D pool, and asked for it on the **main app + gallery preview cards** (widget left untouched).
- **Architecture note — Metal is now in the project.** Earlier notes repeatedly said the water was kept "pure-SwiftUI, no Metal." That constraint was **deliberately relaxed for this feature, at the user's request** — the only way to get real caustics. It's confined to a single `[[ stitchable ]]` SwiftUI fragment shader; there is still no full Metal pipeline / MTKView / SpriteKit / third-party dep.
- **`aqua/Shaders/Caustics.metal`** — one `[[ stitchable ]] half4 caustics(float2 position, float2 size, float time)` function. Classic domain-warped sine-field caustic (4 iterations), normalized against the smaller dimension so cells stay roughly square on the tall water body, `freq = 3.0`. Returns **premultiplied white** (`half4(a,a,a,a)`) so it blends additively. Auto-compiled into the app's `default.metallib` by the `PBXFileSystemSynchronizedRootGroup` (no pbxproj edit needed) and is **app-target only** — `.metal` files under `aqua/` are not in the widget's `membershipExceptions`, so the widget never sees it.
- **`CausticsLayer` (SwiftUI, `ContentView.swift`)** — reusable view used by both call sites. Fills a `Rectangle` with `ShaderLibrary.caustics(.float2(w,h), .float(t))` as a `ShapeStyle`, then `.blendMode(.plusLighter)` + `.opacity(intensity)` (default 0.35) + a top→bottom `LinearGradient` `.mask` so caustics read strongest near the surface and fade with depth. **Time is wrapped** via `time.truncatingRemainder(dividingBy: 1000)` before the `Float` cast — raw `timeIntervalSinceReferenceDate` (~7.8e8) loses too much single-precision resolution and freezes/jitters the animation. Caller passes the raw interval; the layer reduces it.
- **Main app (`waterFillView`)** — `CausticsLayer(...)` inserted in the body ZStack **between the depth gradient and the subsurface glow**, `.clipShape(bodyShape)`. Pure look layer: the `WaveShape`/`WaveCrestShape` geometry, the `waterShapeMask` text color-split sync, and all amplitude/phase/bump math are **unchanged** — so the header dual-layer text mask is unaffected.
- **Gallery (`ThemePreviewCard`)** — the card's single `WaveShape.fill(theme.waterColor)` is now wrapped in a `ZStack { shape.fill(...); CausticsLayer(time:intensity: 0.28).clipShape(shape) }` (slightly lower intensity than the main app since the cards are small). The previous note "Gallery preview cards unchanged" is now superseded for this feature.
- **Widget unchanged** — `AquaWidget.swift` still uses the flat `WidgetWaveShape.fill`. WidgetKit renders static timeline snapshots and can't run a live shader, and the perf budget rules it out anyway.
- **White (not theme-tinted) caustics** chosen on purpose so the one shader reads well over both Default (deep blue) and Kurosawa (charcoal) water without theme tokens — same rationale as the existing white-based depth gradient / specular sheen layers.

### Siri snippet UI — layout constraints + design review (V2.0)
- **User question (Jun 2026):** can the Siri result card be centred or full-width, and can the thin horizontal line at the top-right of the card be removed?
- **Revised after Apple first-party examples (Weather, Messages, Find My):** those cards **do** fill the snippet slot — centred, equal side padding, no trailing dead zone. That is the **design target** WWDC "Design interactive snippets" describes (consistent margins via `ContainerRelativeShape`, snippet fills the container the system hands you). So "full width within the Siri panel" is absolutely the intended look; our left-aligned card with a trailing gap is **not** matching Apple's own snippet presentation.
- **Why ours looks different (third-party App Intents):**
  1. **Known host bug / inconsistency** — [Apple Forums thread 807689](https://developer.apple.com/forums/thread/807689): third-party `ShowsSnippetView` snippets intermittently fail to expand to the offered width (left-aligned, content-sized). Reported on iOS 26.1/26.2 and still seen on iOS 27 per the thread (FB21076429). First-party Siri cards may use a different/plusher host, but the public API is supposed to reach the same full-slot layout when the host behaves.
  2. **Prior in-app experiment** — `View.snippetFillWidth()` (`.frame(idealWidth: 1000, maxWidth: .infinity)`) **did** widen our cards up to the host's max (~85 % of panel), proving the slot *can* be filled from app code when the host cooperates. We later removed that helper in favour of `.frame(maxWidth: .infinity)` + `ContainerRelativeShape()` alone; worth re-testing whether dropping `idealWidth` regressed width on current builds.
  3. **Alternate wiring** — the forum repro splits `ShowsSnippetIntent` → `SnippetIntent` (separate intent returns the view). We return the view directly from `perform()` via `ProvidesDialog & ShowsSnippetView`; unknown if the split pattern affects layout, but it's a low-cost experiment.
- **The top-right line** — still **system UI**: the Siri section divider between the spoken dialog and the snippet slot. It spans the full panel width; when the card is narrower than the slot, the divider extends past the card's trailing edge and reads as "a line on the card." If we recover full-slot width, the divider should sit flush above the card edge (as in Apple's examples) rather than floating in empty space — we still can't remove it, but it stops looking like a card artefact.
- **What *is* changeable — inner card design:** typography, colours, padding, chart, rising-water animation, etc. remain app-controlled.
- **Next steps (TBD):** (a) re-try `idealWidth` + `ContainerRelativeShape` combo on device, (b) try `SnippetIntent` split if width still wrong, (c) file/link Feedback Assistant to FB21076429, (d) inner design pass once outer frame is stable.

### App icon — theme sync fixes (V2.0)
- **Symptom 1:** deleting the build and reinstalling showed SpringBoard's **"App Icon Changed"** alert on first open, before the user touched the theme gallery.
- **Root cause:** `AppIconCoordinator.bootstrapIfNeeded()` treated a fresh install's **primary `Sip` icon** (`alternateIconName == nil`) as misaligned with the Default theme and immediately called `setAlternateIconName("Sip-Aqua")`. That is an alternate-to-"same look" swap with no user action — SpringBoard posts the alert anyway (especially on iOS 27 beta).
- **Symptom 2:** changing theme in the gallery could show the alert but leave the home-screen icon unchanged; the gallery then showed **Applied** (disabled) even though SpringBoard was still wrong, blocking a retry.
- **Root cause:** alignment checks used bookkeeping + `alternateIconName` heuristics that forced the bootstrap swap above; `applyTheme(_:)` skipped icon work when the persisted theme id was unchanged, even if the icon had drifted; silent bootstrap/reconcile swaps could race a user pick; post-dismiss reinforces always re-called `setAlternateIconName` even after a successful swap.
- **Fix (`AppIconCoordinator`):**
  - **`isIconAligned(for:)`** — Default theme is aligned when the reported alternate is **`nil` (primary)** *or* **`Sip-Aqua`**; Kurosawa requires **`Sip-Kurosawa`**. Bootstrap/reconcile now **sync bookkeeping only** when already aligned — no API call on fresh install.
  - **User picks preempt silent swaps** — `applyUserThemeChange` cancels an in-flight bootstrap/reconcile before running.
  - **Default revert fallback** — attempts 1–2 use `Sip-Aqua`; attempt 3 (and silent reinforce) falls back to **`nil` (primary `Sip`)** when reverting from `Sip-Kurosawa`, covering the iOS 26/27 Liquid Glass case where UIKit reports success for `Sip-Aqua` without updating SpringBoard.
  - **Post-dismiss reinforces** — scheduled only when `needsIconSwap` is still true; each tick re-checks before calling again.
  - **`isThemeIconAligned(_:)`** — public helper for the gallery.
- **Fix (`WaterStateViewModel.applyTheme`, `ThemeGalleryView`):** re-run icon swap when the theme id is unchanged but the icon is misaligned; **Applied** pill stays disabled only when both the theme *and* the icon match. Opening the gallery runs a silent `reconcileIfNeeded()` repair pass.
- **Expected behaviour:** fresh install → no icon alert; theme change from gallery → alert + icon update; if SpringBoard drifts, the gallery offers **Set … as theme** again instead of a dead **Applied** state. Persistent failures after 3 attempts — watch Xcode console for `[Aqua] setAlternateIconName` logs; simulator icon cache may need a restart (iOS 27 beta).

### App icon — Icon Composer 2 beta export fix (V2.0)
- **Symptom:** after re-exporting `Sip.icon` / `Sip-Aqua.icon` / `Sip-Kurosawa.icon` from **Icon Composer 2 beta**, the `.icon` bundles showed the generic macOS **"ICON"** document placeholder in Finder/Xcode and the home-screen icon could fail to render.

The orphan catalog set could confuse Xcode's App Icon preview and fallback generation.
  3. **Synchronized-folder package type** — added `explicitFileTypes = { icon = folder; }` on the `aqua` `PBXFileSystemSynchronizedRootGroup` so `.icon` bundles stay opaque packages (not loose `icon.json` / asset members).
- **Fix:** clamped layer-color shadow opacity to **`1`** in all three `icon.json` files; **removed** `AppIcon.appiconset`; set `explicitFileTypes` in `project.pbxproj`. Verified `actool` still emits `Sip60x60@2x.png` + `Assets.car` with the updated refractivity/glass layout.

### iPad Lock Screen — Hydration home widget (V2.0)
- **What it is:** the **`SipHomeWidget`** (`kind: "AquaWidget"`, gallery title **"Hydration"**, `.systemSmall`) — the same small home-screen widget (water fill + "Aqua"/"Sip" header + sip count + log button). It is **not** the accessory **`SipStatusWidget`** (circular/rectangular gauges). iPhone Lock Screen only offers accessory families, so this widget never appears there; it **does** appear on **iPad Lock Screen** because iPadOS also surfaces `.systemSmall` widgets in the lock-screen column (and StandBy on iPhone uses the same family).
- **Why it is new in v2.0:** pre-v2.0 `SipHomeWidget` called `.containerBackgroundRemovable(false)`, which **opts out** of iPad Lock Screen / StandBy — WidgetKit hides non-removable-background widgets from those galleries. The v2.0 glass rework removed that opt-out so the home widget could get Liquid Glass on tinted Home Screens, which also made it eligible for iPad Lock Screen for the first time.
- **Symptom:** on iPad Lock Screen (widget gallery + placed widget), the gray/cream dehydrated panel showed **empty gutters on the left and right** inside the widget frame — unlike the edge-to-edge home-screen widget.
- **Root cause:** the dehydrated backdrop lived only in `containerBackground(for: .widget)`. In iPad Lock Screen / full-color contexts WidgetKit can **inset** the removable container background even when the widget config calls `.contentMarginsDisabled()`, leaving side gutters while the water/chrome layout stayed correct. Home Screen was unaffected because the container background fills normally there.
- **Fix (`AquaWidget.swift`):** follow Apple's WWDC "Bring widgets to new places" pattern — when `widgetRenderingMode == .fullColor` **and** `showsWidgetContainerBackground` (background is visible), mirror `widgetBackground` as a **full-bleed content-layer** bottom `ZStack` child (with `.frame(maxWidth: .infinity, maxHeight: .infinity)` on `homeView`). Keep the existing `containerBackground` declaration so WidgetKit can still remove/replace it in accented / vibrant / Liquid Glass contexts. Accented + vibrant paths unchanged (no content backdrop → wallpaper/glass shows through). Accessory widgets untouched.
